# COST-7687 Gap Analysis: Implement workers and scheduled jobs

**Jira:** [COST-7687](https://redhat.atlassian.net/browse/COST-7687)
**Audited:** 2026-08-10
**Purpose:** Handoff audit vs ticket acceptance criteria. Does not update `docs/tasks.md` or other trackers.
**Beta scope:** ROS and Kruize are **out of beta** ([BETA-PRIORITY.md](BETA-PRIORITY.md)). ROS and Kruize worker AC rows below remain ticket status only — they are **not** Cost beta requirements. Beta cares about Celery on-prem queues (especially SaaS exclusion) and core Beat/workers; ROS sizing/Services and Kruize CronJob sizing are owned by [COST-8054](../jira/COST-8054.md).

## Verdict

Background workloads are largely implemented under `reconcileWorkers`: Celery Beat, the six named on-prem worker queues, ROS poller/housekeeper/partition-cleaner (when `spec.ros.enabled`), and Kruize partition deletion. COST-7687 is **not fully done** for the full ticket (profile-based sizing remains). **G2 (SaaS exclusion)** is addressed by `SaaSCeleryWorkerSpec` with CRD default `replicas: 0` for `hcs`, `subsExtraction`, and `subsTransmission`. **G1 (profile sizing)** remains deferred post-beta → [COST-8095](https://redhat.atlassian.net/browse/COST-8095).

## Done (meets or supersedes ticket intent)

Reconciled in [`reconcileWorkers`](../../internal/controller/costmanagementserviceconfig_controller.go) (pipeline stage after core services):

### Celery

- Beat: [`CeleryBeatDeployment`](../../internal/resources/koku.go) — `celery -A koku beat`, fixed 1 replica
- All six ticket queues via [`CeleryWorkerDeployments`](../../internal/resources/koku.go): `download`, `summary`, `cost_model`, `refresh`, `ocp`, `priority`
- Extra default `celery` queue worker (spec `workers.default`) — useful for beat-scheduled default-queue tasks; supersedes ticket’s six-queue list
- Queue names keep underscores in `WORKER_QUEUES`; Deployment names use `DNS1123Label` ([`names.go`](../../internal/resources/names.go)); covered by [`names_test.go`](../../internal/resources/names_test.go)

### ROS (gated by `ROSEnabled` / `spec.ros.enabled`, default **false**)

- [`ROSPollerDeployment`](../../internal/resources/ros.go) — `recommendation-poller`
- [`ROSHousekeeperDeployment`](../../internal/resources/ros.go) — `housekeeper --sources`
- [`ROSPartitionCleanerCronJob`](../../internal/resources/ros.go) — `housekeeper --partitions`, gated by `spec.ros.housekeeper.partitionCleaner.enabled` (default true), schedule default `0 0 */15 * *`
- Also applies ROS API + Processor in the same stage when ROS is enabled (overlap with COST-7686; not required by this ticket’s wording)

### Kruize

- [`KruizeDeletePartitionsCronJob`](../../internal/resources/kruize.go) — applied from `reconcileWorkers` when ROS enabled and `spec.kruize.partitions.deleteEnabled` (default true)
- Partition **create** runs as init container `create-kruize-partitions` on [`KruizeDeployment`](../../internal/resources/kruize.go) when `createEnabled` (default true); Kruize Deployment itself is applied in core services (also ROS-gated)

### Spec surface

- Per-queue `replicas` / `concurrency` / `resources` under `spec.costManagement.celery.workers.*`
- `scheduleReportChecks` / `reportDownloadSchedule` wired via `KokuCommonEnv`
- ROS/Kruize partition enable + schedule fields as above

## Remaining gaps (ticket-scoped)

### G1. Profile-based sizing — moved to [COST-8095](https://redhat.atlassian.net/browse/COST-8095)

Ticket originally required profile-based sizing. UI already reads `spec.profile`; Celery/Beat maps are owned by COST-8095. ROS/Kruize rows → [COST-8054](../jira/COST-8054.md). Use per-component `spec.*.resources` until those maps land.

### G2. SaaS-only Celery queues not excluded — closed

Ticket: *“SaaS-only queues excluded.”*

[`SaaSCeleryWorkerSpec`](../../api/v1alpha1/costmanagementserviceconfig_types.go) sets `+kubebuilder:default:=0` for `replicas` on `workers.hcs`, `workers.subsExtraction`, and `workers.subsTransmission`. Deployments are still applied (SSA lifecycle) with zero replicas when unset. Opt-in: `hcs: { replicas: 1 }` (or higher) for cloud workloads.

| Queue | Spec field | Default replicas |
|-------|------------|------------------|
| `hcs` | `workers.hcs` | 0 |
| `subs_extraction` | `workers.subsExtraction` | 0 |
| `subs_transmission` | `workers.subsTransmission` | 0 |

On-prem queues (`download`, `refresh`, `ocp`, etc.) keep `CeleryWorkerSpec` default `replicas: 1`.

**Upgrade note:** CRD defaults apply only when the field is omitted. Clusters that already persisted `workers.hcs.replicas: 1` (old default) keep that value until the CR is edited or the field is removed.
